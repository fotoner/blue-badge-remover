# 이슈와 PR

할 일·버그·조사·계획은 GitHub 이슈로 관리한다. 저장소에 계획 문서를 따로 만들지 않는다. 이 문서는 사람과 에이전트가 같이 쓰는 이슈 규칙이다.

## 제목

마침표 없는 한국어 한 줄이다. 종류는 라벨로 나타내므로 `[버그]` 같은 머리말을 붙이지 않는다.

- 버그: 무엇이 어떻게 잘못되는지. 예: `팔로우가 바뀌어도 이미 그려진 인용 카드의 숨김 상태가 바로 바뀌지 않음`
- 기능: 무엇을 하게 되는지. 예: `언어별 선택 필터 팩 — 일본어 먼저, 기본 꺼짐`

## 라벨

이슈마다 **종류 1개 + 우선순위 1개**를 붙이고, 해당하면 영역과 막힘 라벨을 더한다.

| 묶음 | 라벨 |
|---|---|
| 종류 | `bug`, `feature`, `chore`, `research`, `perf`, `epic` |
| 영역 | `area:content`(X 화면 해석·숨김), `area:follow`(팔로우·화이트리스트·계정 데이터), `area:ci`(빌드·시험·배포·스토어 제출) |
| 우선순위 | `P0`(스토어 사용자에게 지금 잘못 동작하거나 저장 데이터를 망가뜨림, 먼저), `P1`(다음에 할 것), `P2`(할 것, 순서 미정), `P3`(아이디어, 할지 미정) |
| 막힘 | `needs:decision`(사용자가 정할 것이 남음), `needs:device`(실기기 확인이 필요함) |

- GitHub 기본 라벨(`enhancement`, `documentation` 등)은 새로 붙이지 않는다. `enhancement` 대신 `feature`를 쓴다.
- 영역 라벨은 같은 영역 이슈가 3개 이상일 때 만들고, 이 표에 먼저 더한다.

## 관계

- 상위 이슈(`epic`)는 하위 이슈를 GitHub 하위 이슈(sub-issue)로 묶는다. 본문에 체크리스트로 다시 적지 않는다.
- 선후 관계는 라벨이 아니라 GitHub의 blocked-by 관계로 건다.

## 본문

틀은 `.github/ISSUE_TEMPLATE/`에 있다. 주장에는 근거 수준을 붙인다: `[확인]`(코드·실측), `[추정]`.

- 사용자 피드백(설문·트위터 제보)에서 온 이슈는 출처를 날짜와 행 번호로 적는다(예: `설문 44행, 2026-10-29`). 응답 원문의 개인정보는 옮기지 않는다.
- 사람이 정할 것이 남으면 `## 결정할 것`에 선택지와 추천을 적고 `needs:decision`을 붙인다.

## 흐름

1. **고르기**: P0 → P1 → P2 순이다. 에이전트가 혼자 진행할 수 있는 이슈는 이렇게 찾는다:
   `gh issue list --search 'is:open -label:epic -label:needs:decision -label:needs:device' --label P1`
2. **작업**: 브랜치 이름 앞에 이슈 번호를 둔다(`fix/100-…`). PR 본문 끝에 `Closes #N`을 적는다.
3. **닫기**: `dev`에 머지할 때 PR의 `Closes`로 닫힌다. 릴리스를 기다리지 않는다. `needs:decision` 이슈와 조사 이슈의 결론은 사용자가 확인한 뒤 닫는다.
4. **릴리스**: `docs/releasing.md`.

## PR

- 틀: `.github/pull_request_template.md`. 문제부터 쓴다: 무엇이 불편했고 이제 어떻게 되는지.
- `## 확인`에는 실행한 명령과 결과 수치(`scripts/check.sh --changed` 포함), 실제 브라우저에서 본 것을 적는다. `.github/workflows/pr-body.yml`이 이 절이 있는지 검사한다.
- `## 미검증`에는 확인하지 못한 경로와 사람이 확인하는 방법을 적는다.
- 리뷰를 받았으면 리뷰어·라운드·판정을 한 줄로 남긴다.

## 공개 저장소 — 넣지 않는 것

AGENTS.md SAFE-8을 따른다. 이슈·PR·댓글에 개인 경로, 토큰·키, 실제 사용자의 X 계정과 그 계정이 보이는 스크린샷, 설문 응답의 개인정보를 넣지 않는다.
